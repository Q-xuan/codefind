# 基线修订与本轮优化

## 已实现

- 单文件 rg 纯数字计数与 Windows 盘符解析修复；非0/1退出不记命中，stderr 不进入匹配分析。
- 输出前递归脱敏 argv、路径和诊断字段；记录 OS、架构、Python/rg 版本、binary SHA-256。Git revision 只表示脚本仓库，不冒充外部 binary 来源。
- 默认测12 anchors，可用 BENCH_MAX_ANCHORS=50 对齐旧基线；新结果写 v2/，历史文件不覆盖。
- 解压准备耗时单列，XML-format 不作为相关性噪声率；保留小数毫秒，去掉硬编码的速度结论。
- 默认12项 XLSX 搜索结果用独立 XML oracle 校验坐标，从真实返回位置 read，校验存储值、预算状态和原始文件哈希。
- 单工作簿不再为工作簿之间的排序单独打开ZIP读取表名；正常内容读取仍排序Sheet，coverage.metadata_status=not_needed。
- Go 范围零命中提示 --lang，不增加自动搜索、不改变默认范围。

## 本机复跑

Windows，rg 15.1.0，Python 3.14.3。修订基线采用每查询1次，仅为流程回归，不是统计性能结论。

- Python 回归5项通过；两套基线脚本完整跑通。
- XLSX readback：10个查询，8个正例回读全部通过；返回坐标全部与oracle一致，原表SHA不变。
- 17个命中单元格的查询在默认预算下返回12项，recall@12为12/17；这属于预算裁剪，不隐瞒为完整召回。
- Windows naive rg 的共享symbol查询识别出3条vendor/minified噪声；此前错误记为0。Scoped rg为0。
- 新结果递归扫描未发现本机绝对目录或用户名；这不是通用秘密扫描证明，提交任何外部查询内容仍需审查。

## 小优化的性能结果

同一fixture/energyMax查询，before和after交替各6次，断言anchors/status/query/limits一致：

| 指标 | before | after |
| --- | --- | --- |
| 进程墙钟中位数 | 511.55 ms | 512.54 ms |
| 工具内部中位数 | 39 ms | 41 ms |

没有观察到可证明的延迟改善；这些波动不支持加速或退化的统计结论。保留这个改动的理由是删除单文件场景无收益的排序预读，而不是宣传性能提升。不要把本机含进程启动的读数与原平台35ms直接拼成同一性能表。

## 后续而非本轮承诺

- 真正的解析性能优化需Go profile区分解压、XML解码、共享字符串和候选投影，不先加缓存或索引。
- rg_unzip仍是预解压计时；端到端竞争基线还需要把解压与坐标重建一起测量，不能用当前速度比作为产品验收。
- 当前XML oracle仅校验夹具中的存储值，不评估业务解释、批注相关性或OCR。
- 固定工具运行顺序的原基线保留其限制；独立compare脚本采用交替顺序，仍未清理OS缓存，也未做显著性检验。
